## Safe release sequence — gate every stage

1. **Identify target**: record the intended Lovable project, bound Supabase
   reference and deployment environment. Distinguish a disposable staging
   clone from the existing production-like Lovable Cloud DB. No direct
   production changes on a "quick test".
2. **Read-only inventory first**: with an authorized DBA account, run
   `scripts/db/preflight-release-0019-0023.sql` in the intended environment.
   This **reads PostgreSQL catalogs only** (no company records). It identifies
   SQL helpers, tables, RLS and direct client write grants. A `true` asset
   presence flag is not proof its migration SQL and policies match source.
3. **Verify migration ledger**: compare the actual
   `drizzle.__drizzle_migrations` entries and SQL content hashes against the
   files in GitHub. If 0017/0018 or any other prerequisite is not applied,
   stop and plan the correct linear order **0017 → 0018 → 0019 → 0020 →
   0021 → 0022 → 0023** (relative to verified 0012–0016); never mark
   a migration applied based on object presence alone. Check for prior manual
   overrides or partially applied scripts before proceeding.
4. **Backup and staging restore**: verify a recent restorable backup, export
   migrations and apply to an isolated staging clone using an account with the
   intended privileges. Perform rollback/migration rehearsal including
   representative non-sensitive test fixtures. **Do not** assume `0023`
   can be rolled back with `DROP TABLE` if business entries exist.
5. **RLS security acceptance**: with separate authenticated sessions, verify
   the company's active super admin can create and void an expense; management
   viewer can see authorized company/project expense reports but cannot write;
   an unrelated company's admin sees nothing; suspended staff, site staff and
   anonymous clients cannot access the data. Check all four WhatsApp tables,
   two expense tables, audit events and RPC grants. Direct DML for ordinary
   `authenticated` actors must remain denied.
6. **Expense functional acceptance**: on a staging-only project and building,
   record ₹120.50 in the Small Expenses page, verify the matching category,
   project, building and date; test a cash expense and an office/no-project
   expense; filter by project, building, category and date; void one with reason
   and confirm that the active totals exclude it but audit history retains it.
   Try invalid amount, impossible building/project and a duplicate request.
   Verify India-local date works while DB timezone is UTC/other.
7. **Material operational acceptance**: start with **700 cement bags**
   on a staging store, issue **300** to Building A and **230** to Building B,
   then return **30** from Building B. Confirm 530 issued, 30 returned,
   **500 net consumed**, and **200 physical on-hand**, *assuming no other
   stock movements*. Check both project/building grouping and per-store
   balances. Independently verify stock ledger quantities, handling returns,
   transfers and a different project/warehouse. Stock is an asset and does
   **not** imply another vendor payment.
8. **Frontend browser acceptance**: verify `/auth`, Finance →
   `/finance/small-expenses`, Materials & Stores →
   `/inventory/material-consumption`, project/building filters, mobile table
   scroll, loading, error and empty states with authenticated sessions.
   Confirm the frontend has the correct **public** Supabase URL and publishable
   key; never expose the service-role key or WhatsApp token.
9. **Operational sign-off**: obtain explicit approval for the identified
   deployment target, database backup, actual migration run and Lovable
   **Publish → Update**. Without this approval, stop after code/CI/docs.
   Review purchase approvals and finance posting separately. Message drafts
   are not actual WhatsApp deliveries.
